# ADR-008 - Uso de xUnit y Data-Driven Testing para Geofencing

## Estado
Aceptado

## Fecha
2026-04-08

## Contexto
El sistema de geofencing de seguridad debe validar reglas de frontera y transiciones de estado para distintos radios de seguridad y condiciones de senal GPS, sin ambiguedad tecnica y con alta mantenibilidad.

Se requiere:
- Evitar duplicacion de codigo en pruebas de multiples radios y distancias.
- Mantener claridad Given-When-Then para escenarios de seguridad.
- Integrar con pipeline .NET y herramientas de cobertura existentes.

El proyecto ya incorpora dependencias de xUnit y Moq en el archivo de proyecto de pruebas.

## Decision
Se adopta xUnit como framework de pruebas principal y el patron Data-Driven Testing como estrategia obligatoria para validar variaciones parametrizadas (radio, distancia, timeout y velocidad aparente).

La implementacion debe usar:
- [Theory] para pruebas parametrizadas.
- [InlineData] para casos simples de frontera.
- [MemberData] o [ClassData] para matrices amplias o escenarios complejos.

## Justificacion tecnica

### 1. Alineacion con escenarios de seguridad
Los criterios incluyen fronteras numericas estrictas (50.0 m, 51.0 m) y multiples variaciones de entrada. Data-driven permite representar estas combinaciones en una sola prueba declarativa por regla.

### 2. Reduccion de deuda tecnica
Sin data-driven, cada radio o distancia generaria metodos duplicados. La parametrizacion reduce duplicacion, facilita mantenimiento y minimiza riesgo de divergencia entre casos equivalentes.

### 3. Trazabilidad y legibilidad
xUnit facilita nombrado expresivo de pruebas y salida clara en CI. Conjuntos de datos pueden vincularse directamente a criterios de CRITERIOS_SEGURIDAD.

### 4. Integracion en ecosistema .NET
xUnit se integra nativamente con dotnet test, cobertura y herramientas de pipeline, sin adaptadores especiales en este repositorio.

## Ejemplo de aplicacion (conceptual)
- Prueba de inclusion de borde con radios/dimensiones:
  - radio=50.0, distancia=49.9, esperado=Dentro
  - radio=50.0, distancia=50.0, esperado=Dentro
  - radio=50.0, distancia=50.1, esperado=Fuera
  - radio=50.0, distancia=51.0, esperado=Fuera

- Prueba de robustez para radios alternativos configurables:
  - radio=30.0 y radio=75.0 con mismas reglas de transicion y unicidad de alerta.

## Consecuencias positivas
- Menor volumen de codigo de prueba repetido.
- Mayor cobertura de combinaciones de riesgo con menor costo.
- Mejor mantenibilidad de la suite de QA.
- Menor probabilidad de regresiones en reglas de frontera.

## Consecuencias negativas
- Curva inicial para modelar datos de prueba complejos.
- Riesgo de tablas de datos excesivas si no se segmentan por dominio.

## Mitigaciones
- Separar datos por capas: geometria, flujo, no funcional.
- Limitar cada conjunto de datos a una sola regla de negocio.
- Versionar datasets con nombre semantico orientado a criterio de seguridad.

## Alternativas consideradas
1. NUnit con TestCase:
- Valido tecnicamente, pero no aporta ventaja clara frente a la base actual ya configurada con xUnit.

2. MSTest con DataRow:
- Integracion posible, pero menor consistencia con estandares actuales del repositorio y menor adopcion en el contexto existente.

3. Pruebas no parametrizadas (duplicadas):
- Descartado por alto costo de mantenimiento y mayor riesgo de inconsistencias.

## Criterios de cumplimiento de esta decision
- Toda regla con umbral numerico debe tener al menos una prueba [Theory].
- Ninguna variacion de radio o distancia debe requerir duplicar metodos de prueba.
- Las clases de prueba deben mantener separacion entre logica geometrica y flujo de alertas.
